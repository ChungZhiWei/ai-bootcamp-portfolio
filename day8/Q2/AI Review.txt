AI Review Task 1 – Review the Data Format

I reviewed both files. The core data is workable — the graph is a single connected component with sufficient information to run a shortest-path algorithm (e.g. Dijkstra/A*) — but there are real gaps for a production pathfinding + visualization system. Here's the breakdown:

What's structurally sound
Connectivity: All 16 nodes (0–15) appear in at least one edge, and tracing the edges confirms the graph is a single connected component (top row 0–5, middle row 6–10, bottom row 11–15, linked by verticals/diagonals). No orphan nodes.
No duplicate edges or self-loops in the 30-edge list.
Undirected + weighted is explicitly stated, which is enough for Dijkstra/A*/BFS with weights.
Distances roughly scale with straight-line coordinate distance (~7–10x factor), so the weights aren't nonsensical relative to layout — though this is coincidental since it's undocumented (see below).

Missing assumptions
Units are undefined. X/Y have no coordinate system (pixels? meters? abstract grid?) and Distance has no unit (meters? seconds? cost?). This matters if you ever mix them (e.g., drawing an edge weight label, or estimating walk time).
No graph directionality guarantee beyond a comment. "Edges are undirected" is a text comment, not enforced by schema — a parser has to trust the file rather than validate it.
No bounds/canvas size for visualization — a renderer has to infer min/max X/Y from the data itself, which is fragile if a future node falls outside expectations.
No node validation guarantee. Nothing stops Graph_Path.txt from referencing a NodeID that doesn't exist in Node_Info.txt (not currently the case here, but there's no schema-level protection — a loader must cross-validate both files).
No versioning/header row — if columns are ever reordered or a field added, older parsers will silently misread data.

Ambiguous fields
Distance vs. straight-line: the note says distance "may be different" from straight-line, but doesn't say why (road curvature? elevation? one-way detours?) — useful for documentation but not for computation, since it's just a flag with no semantic explanation.
TypeID is a closed enum (0–4) with no room for growth (e.g., transit stop, hospital, landmark) and no "unknown/other" fallback — an unrecognized TypeID would break a visualizer's icon-lookup.
Name field uses underscores instead of spaces — fine for whitespace-delimited parsing, but no stated rule about what happens if a name legitimately needs a space, comma, or special character (no quoting/escaping convention defined).
Blank lines in both files seem to group nodes/edges by row/region, but this has no declared meaning — a naive line-by-line parser might choke on them, or a human editor might assume the grouping is semantically meaningful when it isn't.

Edge cases not addressed
Redundant/overlapping edges: e.g., edge 24 (0↔2, dist 300) duplicates the effective path via 0↔1↔2 (120+110=230), and edge 25 (2↔8, dist 310) is longer than the 2↔7↔8 path (190+140=330 — actually longer here, so it's a legitimate shortcut). These aren't bugs, but a shortest-path engine should be tested against them to confirm it picks the true minimum rather than trusting adjacency order.
No isolated-node or malformed-row handling specified — what should the parser do if a future update introduces a typo'd NodeID in an edge? Currently silently connects to nothing/crashes.
No weight sanity constraints (e.g., must Distance be > 0? Can it be 0 for co-located nodes?) — not exploited here, but not guarded against either.
No indoor/multi-level distinction. Malls (TypeID 2) and HDB blocks (TypeID 3) are treated as single points, but if the system ever needs floor-level routing (e.g., "shop inside Central_Mall"), this schema has no way to represent it.
No accessibility/mode data — no field for whether an edge is walkable, drivable, stairs-only, etc. If future routing needs to differentiate transport modes, Distance alone can't encode that.

Recommendation
For pathfinding alone, this is sufficient today. Before scaling it, I'd suggest adding: a units declaration (or a small header/metadata line), edge-mode/type field, ID cross-validation, and either a documented canvas boundary or explicit min/max bounds for the visualizer — none of these are hard requirements to run Dijkstra, but they're the kind of gaps that cause silent bugs once the dataset grows or a second contributor touches the files.

AI Review Task 4 – Review Authentication

Access-control review: pathfinding web app

Good news first: every route that mutates data (/nodes/add, /nodes/edit/<id>, /nodes/delete/<id>, /edges/add, /edges/edit/<id>, /edges/delete/<id>) is correctly decorated with @login_required, and the map view (/) is correctly left open. Route-level authorization is not the problem here — the mechanism enforcing that authorization has several gaps that let it be bypassed entirely.

Critical: hardcoded SECRET_KEY allows session forgery (full login bypass)

app.py sets app.secret_key = "dev-only-change-me" directly in source. Flask sessions are just base64 JSON signed by this key, not encrypted or server-verified against a session store — anyone who knows the key can mint their own valid {"logged_in": True} cookie.

I proved this: using the exact string from the source file, I forged a session cookie, attached it to a fresh, never-authenticated client, and successfully added a node — /login was never called.
Fix: load SECRET_KEY from an environment variable or secrets manager, generate it with secrets.token_hex(32), and never commit it to source control. This single fix closes the most severe hole — everything else is secondary once someone has this key.

High: no CSRF protection on state-changing forms

None of the add/edit/delete forms include a CSRF token, and Flask doesn't add one by default. Combined with cookie-based sessions, this means: if a logged-in admin visits a malicious page while their session is active, that page can silently auto-submit a POST to /nodes/delete/3 (or any other mutation) using the admin's own browser and cookies — no credentials needed, no visible symptom.
Fix: add Flask-WTF's CSRF protection (CSRFProtect(app)), include {{ csrf_token() }} as a hidden field in every form in nodes.html, edges.html, node_form.html, edge_form.html.

High: open redirect via the next parameter

auth.py's login route does redirect(request.args.get("next") or url_for("list_nodes")) with no validation. I confirmed POST /login?next=http://evil-phishing-site.com sends an authenticated user straight to an external URL right after they type their password — a textbook phishing vector, and it makes it easy to trick an authorized user into landing somewhere that then, e.g., asks them to "re-enter" credentials on a fake page.
Fix: only accept relative, same-origin next values (e.g. check next_url.startswith("/") and doesn't start with //), or use werkzeug.urls.url_has_allowed_host_and_scheme.

Medium: single shared credential, no brute-force protection

auth.py hardcodes one username/password pair with no rate limiting on /login. An attacker can attempt unlimited password guesses, and there's no way to tell which authorized person made a given edit (no audit trail — save_nodes/save_edges don't record who or when).
Fix: add login attempt throttling (e.g. Flask-Limiter), move to per-user accounts backed by a real store, and log the acting username alongside each save.

Low / hygiene
Delete buttons rely on a client-side confirm() dialog only — not a security control (trivially bypassed by a direct POST), but worth knowing it provides zero protection on its own; the real protection has to be the auth + CSRF layers above.
Node_Info.txt / Graph_Path.txt live in the app's working directory rather than outside the web root — not a Flask-level issue today (Flask only auto-serves /static/), but worth explicitly keeping them outside any directory a future static-file config might expose.

Priority order to fix
Randomize and externalize SECRET_KEY (closes the full bypass)
Add CSRF protection to all mutating forms
Validate/restrict the next redirect target
Turn off debug=True outside local dev
Add login rate-limiting + move off the single hardcoded credential

AI Review Task 5 – Review Tests and CI Evidence

Good news first: this suite is a genuine step above a smoke test — it starts the real Flask app as a subprocess, drives it over real HTTP, and cross-checks answers against an independent Bellman-Ford reference re-parsed straight from Graph_Path.txt (not by importing Pathfinder.py). That design choice (TC1, TC6) is exactly right and would catch a real Dijkstra bug. But several other tests only check that a request ran, not that the app behaved correctly, and there's an actual infra bug hiding in the harness. Breakdown:

What's genuinely testing behavior
TC1, TC6: compare path and distance against reference_shortest_path() — a real, independent oracle. Solid.
TC2: hardcodes the expected trivial result ([5], 0.0) instead of running it through the oracle. Low risk since it's a degenerate case, but it means TC2 never actually confirms node 5 exists in the graph independently of the app's own claim — it just assumes the app is right if it returns that shape.
TC5: creates two genuinely isolated nodes at runtime and confirms "No Path Exists" — a real fixture-based test, not canned data.

Weak or misleading assertions (false confidence)
TC8 vs TC1 redundancy: TC1–TC6 already run on public = requests.Session(), which is never logged in. So "public pathfinding works without auth" is already proven by TC1. TC8 re-tests the same thing but with a much weaker check ("Shortest path" in resp.text, i.e. presence of the string, not correctness of the value) — it adds the illusion of a new test case without adding new coverage.
TC7 auth coverage is narrow but reported as if broad: only GET /nodes and POST /nodes/add are checked. EditorAuthentication.login_required guards ~8 other routes (/nodes/edit/<id>, /nodes/delete/<id>, /edges, /edges/add, /edges/edit/<id>, /edges/delete/<id>) that are never independently verified. If someone accidentally dropped the decorator from edit_node or delete_edge, this suite would still print "all tests passed."
No test that login itself works correctly — there's no assertion that valid admin/admin credentials actually authenticate (only a print("WARNING…") if the cookie is missing, which doesn't fail the run), and no negative test that a wrong password is rejected. Login success is only inferred indirectly through TC5's fixture setup succeeding.

Missing test cases
Malformed/non-integer start/destination (e.g. ?start=abc). Flask's type=int silently swallows the conversion error and returns None, so the app just renders the plain map with no error message — a real UX gap that's completely untested.
antml:cite index="1-1">app.py, start = request.args.get("start", type=int)`.
Negative or out-of-range but numeric node IDs.
CRUD validation logic in EditorAuthentication.py (empty name, distance ≤ 0, self-loop edge a == b, duplicate edges) is exercised zero times, even though TC5 blindly relies on node/edge creation succeeding.
Cascade-delete correctness (delete_node removing dependent edges) is used by TC5's cleanup step but never verified — nothing checks the "Also removed N connected edge(s)" message or that the graph is actually edge-free afterward.
Only one multi-path scenario (0→8) is checked in TC6; no sweep across other node pairs, no test of a longer multi-hop route (e.g. 0→15).
No concurrency test, despite Pathfinder.py mutating a module-level global graph on every request — a real race-condition risk under concurrent traffic that a sequential test harness structurally can't catch.

Bugs found in the harness itself
Server process leak: cleanup is disabled — stop_server(proc) is commented out in main()'s finally block, so every CI run leaves the Flask subprocess bound to the port. Left unaddressed, this alone would break the next CI run with "port already in use," independent of anything about pathfinding correctness.
Fragile HTML scraping: parse_path_message/parse_error_message depend on exact template markup (<div class="result error">, Shortest path:<br>...<br>Total distance:<br>...<br>). Any copy or markup tweak in index.html breaks parsing and reports a false "FAIL" that looks like a pathfinding regression but isn't.

Bottom line

The core algorithmic claim ("Dijkstra returns the true shortest path") is well-tested via the independent oracle — that part is trustworthy. But the "9/9 passed" summary overstates confidence in two other areas: authorization coverage (2 of ~10 protected routes checked, login success never asserted) and CRUD data integrity (creation/edit/delete validation and cascading deletes are used as untested fixtures, not verified). And the suite currently can't even be re-run cleanly because it leaks the server process it starts.
